# sc6-ping

SOULCALIBUR VI P2P 대전 상대와의 네트워크 지연을 측정하는 도구.

내 PC를 지나는 UDP 패킷을 캡처해 상대 IP를 추정하고, 두 가지를 동시에 잰다.

- **능동** — ICMP 핑으로 왕복 시간(RTT)을 재고 60fps 프레임으로 환산
- **수동** — 상대 패킷의 도착 간격으로 지터와 '프레임 갭'을 계산

결과는 콘솔과 RTSS 오버레이(게임 화면)에 표시된다.

---

## 실행

**스크립트를 먼저 켜고 게임을 나중에 실행한다.**

```powershell
cd C:\Users\FAMILY\projs\sc6-ping
uv run monitor.py
```

게임이 뜰 때까지 대기하다가 자동으로 붙는다. 게임을 꺼도 대기 상태로 돌아가므로 여러 판 연속으로 써도 된다. 종료는 `Ctrl+C`.

로그를 남기려면:
```powershell
uv run monitor.py 2>&1 | Tee-Object -FilePath run.log
```

파이프를 물려도 한글이 안 깨진다 — 콘솔 코드페이지에 맞춰 쓰고 줄 단위로
흘려보낸다(아래 6번). `run.log`에는 상대 IP가 남으므로 `.gitignore`에 넣어뒀다.

### 사전 준비

| 항목 | 상태 | 비고 |
|---|---|---|
| Npcap | 설치됨 | `Restrict to Administrators only`를 **해제**하고 설치해서 관리자 권한 없이 동작 |
| RTSS | 설치됨 | 오버레이용. 트레이에 떠 있어야 하고, **게임보다 먼저** 실행돼야 후킹이 걸린다 |
| uv | 0.9.21 | `uv sync` 한 번이면 준비 끝 |
| ip2asn-v4.tsv | 선택 | 상대 국가/ISP 표시용. 없으면 그 줄만 빠지고 나머지는 그대로 동작한다 |

RTSS 설정에서 `Start with Windows`, `Show On-Screen Display`를 켜두면 이후 신경 쓸 필요 없다.
실행 순서: **RTSS → 게임 → monitor.py**

상대 국가/ISP를 보려면 대역표를 한 번 받아 저장소 폴더에 둔다. 계정이 필요 없고
받아두면 완전히 오프라인으로 동작한다 — **상대 IP가 밖으로 나가지 않는다.**

```powershell
curl.exe -L -o ip2asn-v4.tsv.gz https://iptoasn.com/data/ip2asn-v4.tsv.gz
# 압축 해제 후 ip2asn-v4.tsv 로 저장소 폴더에 둔다
```

기동할 때 `[*] 국가/ISP 표: ...` 한 줄로 상태를 알려준다. 파일이 없으면
`없음 (국가/ISP 표시 안 함)`이 뜨고 나머지 기능은 그대로다.

## 출력 읽는 법

```
22:24:43  115.143.25.127   48.0ms → 2.9프레임  간격 16.6ms  지터 0.2  갭 0.0/s(최대 17)  132pkt/s ↑66↓66
```

한 줄이다. **간격·지터·갭의 단위는 전부 ms**이고, 반복을 피해 첫 필드에만 붙인다.

| 항목 | 뜻 |
|---|---|
| `48.0ms` | ICMP 왕복 시간 |
| `2.9프레임` | 왕복 시간 ÷ 16.67ms. **왕복 기준**이며 게임이 실제로 넣는 입력 딜레이는 대략 이 절반(편도) |
| `간격` | 상대 패킷 도착 간격의 중앙값. 정상 대전이면 **16.6ms** |
| `지터` | 도착 간격의 p95 − p50. 표준편차 대신 백분위를 써서 스파이크 하나에 값이 흔들리지 않게 함 |
| `갭` | 간격이 2프레임을 넘은 횟수/초, 괄호 안은 최악의 간격. **딜레이 기반에서 게임이 멈춰 기다린 횟수** |
| `132pkt/s ↑66↓66` | 초당 패킷 수와 방향별 내역 |
| `(비페이싱)` | 프레임당 1패킷 구조가 아니라 지터·갭이 성립하지 않는 스트림 |
| `간격 --(표본 3/5)` | 통계를 낼 만큼 안 모였다는 뜻. **잰 값이 0인 게 아니다** |
| `>=` 접두사 | TTL 폴백으로 잰 하한값. 실제는 이보다 크다 |
| `핑 무응답` | ICMP가 막힌 것. 사유와 폴백 홉은 `[*]` 안내로 한 번만 나온다 |
| `손실 %` | 핑 손실률. **`>=`가 붙어 있을 때는 아예 안 나온다** — 그 손실은 상대가 아니라 중간 라우터의 ICMP rate-limit이라 게임 손실로 오해된다 |

상대가 ICMP를 막으면 `핑 무응답`이 먼저 나오고, tracert가 폴백 홉을 찾은 뒤
(약 14초) `>=`가 붙은 값으로 바뀐다. 그 사이 오버레이에는 `SC6  ping --`이 뜬다.

콘솔 줄은 터미널 폭을 넘지 않게 잘린다(잘리면 끝에 `…`). 넘긴 줄이 다음 출력과
겹쳐 글자가 섞이는 걸 막기 위한 것이다.

SC6는 **딜레이 기반 넷코드**라 늦게 온 패킷을 되감아 보정하지 못하고 그냥 기다린다.
그래서 평균 핑보다 **갭이 튀는 순간**이 체감을 좌우한다. 평균 핑이 낮아도 갭이 있으면 버벅인다.

## 판 요약과 평가

판이 끝나면 그 판 전체를 한 번에 정리한다.

```
[판 종료] 14.47.163.10  한국 · Korea Telecom (AS4766)   3분 18초
  평가  A   (핑 A / 지터 A / 갭 A)
  핑    4.4ms → 0.3프레임 왕복 (편도 0.1)
  간격  16.3ms
  지터  중앙 1.0ms   최대 98.0ms
  갭    18회   최악 128ms   (5.5회/분)
  굶음  42프레임 / 11,880   (0.35%)
```

게임을 끄거나 `Ctrl+C`로 나가면 그 세션의 판들을 한 번 더 묶어 보여준다.

### 갭은 횟수가 아니라 '굶은 프레임'으로 잰다

갭 횟수는 **30ms 갭과 490ms 갭을 똑같이 1회로 센다.** 앞은 체감이 없고 뒤는
눈에 보이는 멈춤이다. 그래서 등급은 횟수가 아니라 **굶은 프레임 비율**로 낸다.

```
굶은 프레임 = Σ (간격 ÷ 16.67ms − 1)      ← 갭으로 잡힌 간격만
비율        = 굶은 프레임 ÷ (판 길이 × 60)
```

간격 50ms면 2프레임, 490ms면 28프레임을 굶은 것이다. 게임이 실제로 몇 프레임을
멈춰 기다렸는지라 정의상 확실하고, 판 길이가 달라도 비교된다.

**이걸 왜 바꿨나:** 처음엔 갭 횟수로 등급을 냈는데, 국내 4.4ms 판(아래 실측)이
7.6회/분이라 **D를 받았다.** 핑 4.4ms에 지터 1.0ms인 최상급 판이다. 같은 판을
비율로 재면 0.35%로 A가 나온다.

### 등급 임계값 — 근거의 강도가 다르다

**이 세 줄을 같은 무게로 읽으면 안 된다.**

| 항목 | 근거 | 임계값 |
|---|---|---|
| **굶음** | 실측 두 점에 기댄다 (아래). 지표 자체는 정의상 확실하지만 경계선은 조정 여지가 있다 | ≤1% A / ≤3% B / ≤10% C |
| 핑 | 격겜 통념(편도 2~3프레임까지 무난)에 기댄 값 | 편도 ≤1f A / ≤2f B / ≤3f C |
| **지터** | **추측이다.** 실측이 정상(0.4~2ms)과 렉(338~470ms) 두 극단뿐이고 중간 지대 데이터가 없다 | ≤2ms A / ≤10ms B / ≤30ms C |

굶음 임계값의 실측 근거:

| 판 | 굶은 프레임 비율 |
|---|---|
| 국내 4.4ms, 3분 18초 (2026-08-24) | **0.35%** ← 최상급 |
| 렉 구간 6초 (132 → 16pkt/s) | **수십 %** ← 명백한 렉 |

종합은 **셋 중 최악**이다. 평균을 내면 게임이 멈춘 판이 "지터는 좋았으니까"로
희석되는데, 굶음은 게임이 실제로 멈춘 시간이라 다른 지표로 상쇄될 성질이 아니다.

핑이 `>=`(폴백 홉 하한)이면 실제 등급은 표시된 것보다 **나쁠 수는 있어도
좋을 수는 없다.** 그 사실을 요약에 한 줄로 밝힌다.

### 판의 시작과 끝

`Flow.frame_paced`이고 속도가 `KEEP_RATE` 이상이면 대전 중으로 본다.
끝나는 경우는 셋이다.

| 조건 | 처리 |
|---|---|
| 대전 조건이 **12초**(`MATCH_END_GRACE`) 연속 거짓 | 마지막 정상 시각으로 잘라 마감 |
| 상대 IP가 바뀜 | 확정적 경계. 즉시 마감 |
| 게임 종료 / `Ctrl+C` | 진행 중이던 판을 그대로 마감 |

**12초인 이유:** 렉과 판 종료는 처음 2초 동안 구별이 안 된다. 실측된 렉은
6초짜리였다(132 → 16 → 132pkt/s). 그 두 배를 뒀다.

**유예 구간의 표본은 통계에 안 넣는다.** 붕괴 중에는 지터가 400ms대로 튀는데
그걸 섞으면 멀쩡한 판도 전부 나쁘게 나온다. 판의 끝은 마지막으로 정상이던
시각으로 자른다.

30초 미만은 요약을 내지 않는다(`MATCH_MIN_SECONDS`) — 매칭 단계의 순간
스파이크가 '판'으로 잡히는 걸 막는다.

**판을 시작하려면 ↑↓가 대칭이어야 한다**(`MATCH_START_SYMMETRY`, 수신이 송신의
80% 이상). 연결 수립 중에는 송신이 먼저 붙고 수신이 뒤따르는데, 그 구간은
대전이 아니라 접속 중이라 갭이 몰려 있다. 실측:

```
23:56:29   96pkt/s ↑66↓30   갭 3.5/s(최대 265)   ← 수립 중. 갭 25회 중 7회가 여기
23:56:31  126pkt/s ↑64↓62   갭 1.0/s(최대  64)   ← 여기서 판 시작
23:56:33  132pkt/s ↑66↓66   갭 0.0/s
```

대칭은 **시작 조건에만** 쓴다. 판 도중의 비대칭은 렉일 수 있고, 그게 종료인지
렉인지 가를 근거가 아직 없다.

> 표본은 **2초 로그 틱에서만** 모은다. `JITTER_WINDOW`가 정확히 2.0초라
> 창이 겹치지 않아서다. 250ms 표시 틱에서 모으면 같은 패킷을 8번 세서
> 갭 횟수가 8배로 부푼다.

## 실측으로 확인된 것

재현·재검증할 필요 없는 사실들. 수정할 때 이 전제를 깨지 않도록 주의.

### 국내 상대는 4ms대가 나온다 (2026-08-24)

`14.47.163.10`과 3분 18초. **핑 4.4ms → 편도 0.1프레임.** ICMP도 정상 응답해서
`>=` 폴백이 필요 없었다.

```
23:57:33  14.47.163.10  4.5ms → 0.3프레임  간격 16.4ms  지터 1.1  갭 0.0/s  132pkt/s ↑66↓66
```

여기서 확인된 것:

- **프레임당 1패킷 전제가 다시 확인됐다** — 간격 16.3~16.6ms, `↑66↓66` 정확히 1:1
- **ICMP에 응답하는 상대가 실제로 있다** — 지금까지는 전부 막혀 있었다
- **갭 집계가 정확하다** — 2초 로그의 갭을 손으로 세니 25회, 요약도 25회.
  창이 겹쳐 8배로 부풀지 않는다는 걸 실측으로 확인했다
- **판 경계가 맞다** — 3분 18초, 요약이 한 번만 떴다

### 대전 트래픽은 프레임당 1패킷이다

| | 값 |
|---|---|
| 수신 도착 간격 (실측) | **16.6 ms** |
| 60fps 프레임 시간 | 16.67 ms |

이게 `FRAME_GAP_FACTOR = 2.0`(2프레임 초과 시 갭)의 근거다. 임계값을 임의로 정한 게 아니라 실측에서 나왔다.

### 매칭 잡담 vs 실제 대전

로그에 같은 IP(`115.143.25.127`)가 잡담에서 대전으로 넘어가는 전 과정이 찍혔다.

```
22:24:20   8pkt/s   ↑9   ↓8    간격 89.1ms   (프레임 페이싱 아님)
22:24:35  52pkt/s   ↑90  ↓14   간격 21.9ms   지터 454ms
22:24:37  76pkt/s   ↑139 ↓13   간격 73.8ms              ← 송신만 폭증
22:24:41 114pkt/s   ↑143 ↓84   간격 16.6ms   지터 1.0ms  ← 수신이 따라붙음
22:24:43 132pkt/s   ↑132 ↓132  간격 16.6ms   지터 0.2ms  갭 0  ← 대전 시작
```

3분 뒤 정확히 역순으로 붕괴한다. 판별 기준:

| | 매칭 잡담 | 실제 대전 |
|---|---|---|
| 속도 | 4~18 pkt/s | **132 pkt/s** |
| 도착 간격 | 제각각 (0/42/89/240ms) | **16.6ms 고정** |
| ↑↓ 대칭 | 들쭉날쭉 | **정확히 1:1** |

대전 상대는 동시에 여럿일 수 없다. 여러 IP가 번갈아 잡히면 매칭 단계다.
(패킷 내용은 파싱하지 않으므로 "매칭 프로브"라는 해석 자체는 행동 기반 추론이다. 확실한 건 "대전이 아니다"까지.)

### 스팀 릴레이는 상대가 아니다

SC6는 상대와 직결하면서 **동시에 스팀 릴레이로도 같은 스트림을 흘린다.** 릴레이 쪽 패킷이 근소하게 많을 때가 있어 그냥 두면 릴레이가 상대로 뽑히는데, 릴레이는 ICMP를 100% 드롭한다(실측: `146.66.152.43` 손실 2/2).

`VALVE_NETWORKS`(AS32590 광고 prefix를 집약한 11개 대역)로 걸러낸다.

### `pkt.time`을 써야 한다

10ms 간격으로 정확히 쏴서 비교:

| 타임스탬프 소스 | 중앙값 | 표준편차 |
|---|---|---|
| `pkt.time` (Npcap 드라이버) | 10.00 ms | **0.06 ms** |
| 파이썬 콜백 시각 | 10.02 ms | **3.07 ms** |

16.6ms를 재는 지표에 3ms 노이즈가 섞이면 무의미해진다. 반드시 `pkt.time`.

### scapy `sniff()`는 Ctrl+C를 삼킨다

`sniff()`의 기본값이 `chainCC=False`라 `KeyboardInterrupt`를 잡아먹는다(`sendrecv.py:1387`). 게다가 내부 select가 남은 타임아웃 전체를 블로킹해서 시그널 처리도 안 된다.

그래서 `AsyncSniffer`를 데몬 스레드로 돌리고 메인은 `time.sleep(0.2)`를 반복한다. Windows에서 `time.sleep`은 Ctrl+C로 즉시 깨어난다.

`subprocess.run()`도 같은 이유로 안 쓴다(인터럽트 시 3초 붙잡힘) — `Popen` + 폴링.

### RTSS는 DLL export가 아니라 공유 메모리

`RTSSHooks64.dll`에 `UpdateOSD` 같은 export는 없다. 서드파티 텍스트는 `RTSSSharedMemoryV2` 공유 메모리로 넣는다(`SDK/Include/RTSSSharedMemory.h`). 구조체가 오프셋·크기를 스스로 알려주므로 하드코딩하지 않았다.

`dwBusy` 비트는 반드시 `try/finally`로 해제할 것 — 안 내리면 모든 프로그램의 OSD 갱신이 잠긴다.

### ping 출력은 cp949다

`text=True`로 받으면 UTF-8 디코드 실패로 리더 스레드가 죽고 `stdout`이 `None`이 된다. 바이트로 받아 `GetOEMCP()` 인코딩으로 직접 푼다.

파싱도 `TTL=`이 있는 응답 줄만 골라야 한다. 예전 토큰 방식은 `바이트=32`의 **32를 핑으로 반환**하는 버그가 있었다.

## 반영되고 실전에서 검증된 변경

전부 2026-08-23 실제 대전(상대 `106.5.205.155`, 3분 2판)에서 확인했다.
왜 그렇게 고쳤는지가 남아 있어야 다시 건드릴 때 같은 실수를 안 한다.

### 1. `MIN_RATE` 상향 — 검증됨

`MIN_RATE = 5.0` → **50.0**. 실제 대전 132pkt/s, 매칭 잡담 4~18pkt/s가 근거다.
같이 들어간 것 두 가지:

- `KEEP_RATE = MIN_RATE / 2` — 새로 잡을 땐 50, 이미 고른 상대는 25까지 떨어져도 유지.
  임계값만 올리면 132pkt/s가 순간 흔들릴 때 상대를 놓아 EMA·핑 이력·`_traced`가 통째로 리셋된다.
- `ProbeCache` — `pick_opponent()`는 **메인 스레드**에서 돈다. 예전엔 재선정마다 후보를
  다시 찔러서, ICMP 막힌 상대면 5초 주기로 최대 3.6초씩 화면이 멈췄다. 대전 중에는
  히스테리시스로 조기 반환하므로 프로브가 아예 안 돈다.

합성 시퀀스 13종 통과(잡담 배제/대전 채택/순간 하락 유지/붕괴 해제/릴레이 공존/캐시 적중·만료).
게임 실행 상태에서 유휴 동작도 확인 — 상대를 잡지 않고 `대전 트래픽 없음`만 남긴다.

**실측 결과:** 상대 IP가 판 내내 `106.5.205.155` 하나로 고정됐다. 중간에
다른 IP로 튀지 않았고, `ICMP 차단` 안내도 판당 한 번만 나왔다. 2초 로그의
타임스탬프는 한 번도 안 밀렸다 — 트래픽이 132→16pkt/s로 무너진 렉 구간에서도.

그 렉 구간이 히스테리시스의 증거다. 16pkt/s는 `KEEP_RATE`(25) 아래인데도
상대를 놓지 않았고, 4초 뒤 132pkt/s로 복귀했을 때 EMA와 핑 이력이 그대로였다.

```
22:30:10  >=55.5ms  간격 16.6ms  지터  0.7  갭 0.0/s   132pkt/s ↑66↓66
22:30:12  >=55.3ms  간격 16.0ms  지터 338.0  갭 4.5/s    28pkt/s ↑14↓14   ← 렉
22:30:14  >=55.3ms  간격 19.2ms  지터 470.6  갭 3.0/s    16pkt/s          ← KEEP_RATE 아래
22:30:20  >=55.3ms  간격 16.6ms  지터  0.6  갭 0.0/s   130pkt/s ↑66↓64   ← 복귀, 상대 유지
```

### 2. 로그 줄 폭 — 검증됨

```
22:49:48  101.141.49.46    핑 무응답 (ICMP 차 단)   ...  s (↑4 8pkt/s (↑4 ↓4)
```
한글 전각 폭 + 줄바꿈이 엉킨 PowerShell 렌더링 문제였다.

원인 측정: 문제의 줄은 **122자였지만 실제 폭은 139칸**이었다. 한글이 두 칸인 데다
`→`·`↑`·`↓`는 `east_asian_width`가 `A`(ambiguous)로 분류하는데 cp949 콘솔에서는
두 칸으로 그려진다. 글자 수로 세면 절대 안 맞는다는 게 핵심.

들어간 것:

- **중복 제거** — `(최소/최대)`, `(하한 N홉)`, `(ICMP 차단)` 삭제. 셋 다 `[*]` 1회성
  안내나 `>=` 접두사가 이미 말하고 있었다. `(프레임 페이싱 아님)` → `(비페이싱)`,
  단위 `ms`는 그룹의 첫 필드에만.
- **`display_width()` / `fit_width()`** — `W`/`F`/`A`를 전부 두 칸으로 세고 터미널 폭
  (`shutil.get_terminal_size`, 파이프면 120)에 맞춰 자른다. 넉넉히 세는 쪽이 안전하다 —
  조금 일찍 잘릴 뿐 줄이 넘쳐 엉키지는 않는다. 새 의존성 없음.

측정 결과 **139~150칸 → 107칸**(정상 대전), 최악 119칸(손실 표시 동반). 합성 13종 통과
(경계 폭, 전각 절단 시 글자 안 쪼개짐, 80칸 창, 파이프 fallback).

**실측 결과:** 실제 PowerShell 창에서 섞인 줄이 한 줄도 없었다. 단, 파이프로
넘길 때 한글이 통째로 깨지는 **다른** 문제가 드러났다 — 폭이 아니라 인코딩이다.
아래 6번.

### 3. 표본 부족 표시 — 검증됨

`Flow.__init__`은 표본이 모자라면 통계를 전부 0으로 뒀는데, 출력은 `간격 0.0ms`라
**측정해보니 0**인 것처럼 보였다. 게다가 `median_gap = 0`은 `frame_paced` 판정도
통과 못 해서 `(프레임 페이싱 아님)`으로 찍혔다 — 두 번 틀린 셈이다.

들어간 것:

- 매직넘버 `5` → `MIN_GAP_SAMPLES` 상수
- `Flow.sampled` / `Flow.gap_samples` — '잰 값'과 '아직 안 잼'을 상태로 구분.
  0은 값이 아니라 '측정 안 함'이라는 주석을 해당 분기에 남겼다
- 표본이 모자라면 `간격 --(표본 3/5)` — 몇 개나 모였는지까지 보여줘서
  잠깐 부족한 건지 계속 안 차는 건지 구분된다

`frame_paced ⇒ sampled` 불변식이 성립하므로 OSD의 `JIT`/`GAP`도 표본 부족일 때는
아예 안 뜬다(가짜 0이 안 나간다). 합성 19종 통과 — 경계(4/5/6개), 표본 부족 표기,
비페이싱과의 구분, OSD 불변식, 폭 회귀(최대 106칸).

### 4. 포트 목록 요동 — 검증됨

실측 추이 `3→7→9→19→3→47→58`. 바뀔 때마다 스니퍼를 껐다 켜서 그 순간 패킷을 놓쳤다.
16.6ms를 재는 도구가 재시작하는 수백 ms를 눈감으면 지터·갭이 실제보다 나쁘게 나온다.

들어간 것:

- **`PortSet`** — 세션 동안 본 포트를 합집합으로 누적. 목록이 늘기만 하므로 재시작은
  '새 포트가 처음 보일 때'로 한정되고 곧 멈춘다. 상한에 걸리면 **가장 오래 못 본 포트부터**
  버린다(LRU) — 지금 열려 있는 포트는 매 주기 갱신되므로 절대 밀려나지 않는다.
- **빈 목록에 누적분을 안 버린다** — `psutil.net_connections()`는 일시적 권한 오류로
  빈 리스트를 줄 수 있다. 예전엔 그때마다 폴백 필터로 떨어져 캡처 범위가 널뛰었다.
- **버린 포트 수를 로그에 남긴다** — 상한을 조용히 넘기지 않는다.

#### `MAX_FILTER_PORTS`를 60 → 200으로

예전 주석의 "포트당 BPF 명령 10개 남짓"은 **과대 추정이었다.** `compile_filter`로
`bf_len`을 직접 셌다:

| 포트 수 | BPF 명령 | 포트당 |
|---|---|---|
| 60 | 197 | 3.3 |
| 120 | 490 | 4.1 |
| 200 | 969 | 4.8 |
| 250 | 1269 | 5.1 |

libpcap 한도는 `BPF_MAXINSNS = 4096`이다. 200포트여도 969명령, 한도의 24%다.
실측 포트 수가 58까지 갔던 걸 감안하면 3배 넘는 여유가 생긴다.

**효과 (합성 20스냅샷, 같은 소켓 풀에서 매번 다른 부분집합이 보이는 모델):**

| | 예전 | 지금 |
|---|---|---|
| 스니퍼 재시작 | 20회 | **7회** |
| 포트 커버리지 평균 | 63% | **83%** (끝에는 100%) |

합성 20종 통과. 첫 모델은 포트를 중첩 증가로 뒀더니 매 단계가 진짜 새 포트라
재시작이 7→6밖에 안 줄었다 — 실제 요동은 '같은 풀의 다른 부분집합'이라 위 모델이 맞다.

### 5. `tracert`가 Pinger를 멈춤 — 검증됨

막힌 경로에서 `20홉 × 3프로브 × 0.4s` = 24초. 그 동안 핑을 한 발도 못 쐈고,
상대가 바뀐 것도 못 알아챘다. 같은 IP에 두 번 실행된 사례도 있었다.

들어간 것:

- **`-h` 20 → 12** (`TRACE_MAX_HOPS`). 최악 24초 → 14.4초. deadline도 상수에서 계산한다
- **추적을 Pinger 루프에서 떼어냈다** — 별도 데몬 스레드로 돌린다. 추적하는 동안에도
  핑이 계속 나가고 상대 교체도 즉시 반영된다. README가 요구한 건 `-h` 축소와 캐시뿐이지만,
  제목이 말하는 '멈춘다'는 그 둘로는 안 없어진다
- **IP별 추적 캐시** (`_trace_cache`, LRU 32) — `set_target()`이 `_traced`를 리셋해도
  캐시는 남으므로 같은 상대를 다시 골라도 tracert를 다시 돌리지 않는다.
  '찾아봤지만 홉이 없더라'는 결과도 캐시한다. 단 **종료 중 끊긴 결과는 캐시하지 않는다** —
  '홉 없음'으로 굳으면 다음 세션에서 멀쩡한 경로도 포기한다
- **`TraceHop.truncated`** — `-h`를 줄인 대가로, 홉 한도에 걸려 끊긴 추적과 경로가
  진짜 죽은 것을 구별할 수 없게 됐다. 한도에 걸린 경우 안내에 `12홉까지만 추적`을 붙여
  하한이 경로 중간에서 잰 값일 수 있음을 밝힌다. `weak` 판정 자체는 그대로 둔다

#### 덤: `Pinger._stop`이 `Thread._stop`을 덮어쓰고 있었다

`threading.Thread._stop`은 **실제로 존재하는 내부 메서드**다. `Pinger.__init__`이
`self._stop = threading.Event()`로 이걸 덮어써서, `Thread.join()`을 부르면
`'Event' object is not callable`로 터진다. 데몬 스레드라 join을 안 해서 드러나지
않았을 뿐 언제든 밟을 수 있는 지뢰였다. `_stopped`로 바꿨다.

합성 12종 통과 — 추적 중 핑 발사 지속(0.6초 동안 10발, 예전엔 0발), 재선정 시 추적 1회,
다른 추적이 도는 중에도 새 상대가 결국 추적됨, 종료 중 결과 미캐시, 캐시 상한, `weak` 회귀.

### 6. 파이프로 넘기면 한글이 깨짐 — 검증됨

```
22:29:14  106.5.205.155  >=55.5ms ??3.3?꾨젅?? 媛꾧꺽 16.6ms  吏??0.7
```

폭 문제가 아니라 **인코딩 불일치**다. 콘솔에 직접 쓸 때는 파이썬이
`WriteConsoleW`로 유니코드를 그대로 넘겨 인코딩을 안 탄다. 그런데
`| Tee-Object`처럼 파이프를 물리면 바이트로 나가고, PowerShell은 그걸
`[Console]::OutputEncoding`(= 콘솔 코드페이지, 이 PC는 949)으로 되읽는다.
이 PC엔 `PYTHONUTF8=1`이 잡혀 있어 파이썬은 UTF-8로 쓴다. 그래서 어긋난다.

숫자만 ASCII라 멀쩡히 남는 게 이 증상의 특징이다.

들어간 것:

- **`match_console_encoding()`** — 파이프일 때만 `GetConsoleOutputCP()`에 맞춰
  `stdout`/`stderr`을 `reconfigure`한다. `isatty()`면 건드리지 않는다
- **`line_buffering=True`** — 같이 켠다. 파이프면 파이썬이 8KB 블록 버퍼링을
  쓰는데, 2초에 한 줄(약 100바이트) 내는 도구라 화면이 2분 넘게 밀린다
- **출력 문자열의 em dash를 horizontal bar로** (7곳) — cp949에 `—`(U+2014)와
  `–`(U+2013)가 없다. `―`(U+2015)는 있고 `east_asian_width`도 똑같이 `A`라
  `fit_width()` 결과가 안 바뀐다. 독스트링은 화면에 안 나가므로 그대로 뒀다
- **OSD 대기 문구를 영문으로** — RTSS `szOSD`는 char 배열이고 `show()`가
  `encode("ascii", errors="replace")`를 해서 `SC6  대기 중`이 `SC6  ?? ?`로 떴다

검증: 출력 줄 13종이 cp949 왕복 무손실(최대 119칸). 파이프로 실제 기동해
바이트를 확인 — cp949로 디코드되고 즉시 흘러나온다.

### 7. 폴백 대기 19초 동안 오버레이가 비었다 — 검증됨

상대가 ICMP를 막으면 오버레이가 `SC6  ping --`로만 떠 있었다. 내역:

| 구간 | 시간 | 근거 |
|---|---|---|
| 핑 3연속 실패 대기 | 5초 | `FAILS_BEFORE_TRACE` × `PING_INTERVAL` |
| tracert 12홉 | 14초 | `TRACE_MAX_HOPS` × 3프로브 × `TRACE_PROBE_MS` |

한 판이 3분인데 19초가 비었다. 들어간 것:

- **상대를 잡자마자 추적을 시작한다.** 핑 3회 실패를 기다리지 않는다. 추적은
  이미 별도 스레드(5번)라 핑을 안 막고, 상대가 ICMP에 응답하면
  `trace_last_hop()`이 `None`을 주므로 결과는 그냥 안 쓰인다
- **`_record_trace` / `_use_trace_if_needed` 분리.** 즉시 시작하면 추적 결과가
  '핑이 막혔다'는 판정보다 먼저 올 수 있다. 그때 바로 적용하면 ICMP에 멀쩡히
  응답하는 상대까지 홉 RTT(하한)로 바꿔 표시하게 된다. 받아두기만 하고
  `_fails >= FAILS_BEFORE_TRACE`가 될 때 쓴다

**실측: 19초 → 14초.** 남은 14초는 tracert 자체다.

```
22:50:40  106.5.205.155  핑 무응답 ...          ← 상대 선정
22:50:54  106.5.205.155  >=55.0ms → 3.3프레임    ← 14초 뒤
```

합성 27종 통과 (즉시 시작/응답하는 상대엔 미적용/문턱 전 보류/상대 교체 시
리셋/캐시 1회/weak 거부/LOSS 표시).

#### 덤: `손실 %`는 상대가 아니라 중간 라우터의 것이었다

폴백 홉을 재는 동안 `손실 10~33%`가 찍혔는데, 이건 11홉 라우터가 ICMP를
rate-limit하는 것이지 상대와의 손실이 아니다. 같은 시각 대전 연결은
`132pkt/s ↑66↓66`으로 멀쩡했다. 오버레이에 `LOSS 20%`가 뜨면 게임이 끊기는
걸로 읽을 수밖에 없어서, **폴백 중에는 콘솔·OSD 양쪽에서 숨긴다.**

## 검증 완료 (재확인 불필요)

- **오버레이가 게임 화면에 실제로 뜬다.** 오래 미확인이던 항목이다. 공유 메모리를
  직접 덤프해 확인: 슬롯 0, `owner='sc6-ping'`,
  `text='SC6  >=64ms  >=3.8f  JIT 1.0  GAP 0.0'`. SC6도 RTSS 후킹 목록에 있었다
- **ICMP를 막는 상대가 실제로 있다.** `106.5.205.155`가 그랬고, TTL 폴백이
  `182.110.211.122`(12홉)를 찾아 `>=55.0ms → 3.3프레임`을 냈다. 하한 표기(`>=`)와
  `12홉까지만 추적` 안내가 의도대로 붙었다
- 프레임당 1패킷 (실측 16.6ms vs 이론 16.67ms)
- `pkt.time` 정확도 (표준편차 0.06ms)
- 지터·프레임 갭 계산 — 합성 시퀀스 9종 통과 (규칙적/누락/흔들림/표본부족/창만료/방향분리/버스트)
- Ctrl+C 응답 0.01~0.09초, `ping.exe`·`TRACERT.EXE` 잔류 없음
- 메모리 24초 4.2MB 고정 (deque `maxlen`으로 제한)
- 대기 → 감지 → 세션 → 대기 전환
- RTSS 미설치·미실행 시 no-op으로 떨어지고 콘솔은 정상 동작
- TTL 폴백이 경로가 일찍 끊기면 추정을 거부 (엉터리 숫자를 만들지 않음)

## 알려진 문제 / 다음 작업

### 판 요약 — 코드 반영됨, 실전 미검증

합성 46종은 통과했다(실측 렉 구간 재생, 붕괴 판정, 유예 구간 배제, 갭 8배
부풀림 회귀, 등급 경계, GeoDB 없음·정상·형식깨짐, 폭·cp949). 하지만 **실제
대전에서 판 경계가 제대로 잡히는지는 아직 못 봤다.**

확인할 것:

- 판이 끝났을 때 요약이 한 번만 뜨는가 (중복/누락 없이)
- 요약의 갭 횟수가 로그를 손으로 센 것과 맞는가 ← 8배 부풀림 회귀
- **판 사이 간격이 12초보다 짧으면 두 판이 하나로 붙는다.** SC6는 결과 화면과
  재대전 대기가 있어 안전할 것으로 보지만 **재본 적이 없다**
- 상대 국가/ISP가 맞게 나오는가

### 지터 임계값에 근거가 없다

위 '판 요약과 평가' 표의 지터 값은 추측이다. 정상(0.4~2ms)과 렉(338~470ms)
사이의 데이터가 없어서, 지터 15ms짜리 판이 실제로 어떤 느낌인지 모른다.
판이 쌓이면 다시 볼 것.

### 렉과 판 종료를 더 빨리 구별할 수 있을지 모른다

README에 찍힌 진짜 붕괴는 ↑↓ 비대칭이 특징이다(`↑139 ↓13`). 렉일 때도
그런지 알면 12초를 안 기다리고 2~4초 만에 구별할 수 있다. 그런데 실측된 렉
구간의 ↑↓ 값이 남아 있지 않다. **다음에 렉이 잡히면 그 줄을 보관할 것.**

### 폴백 대기 14초

7번으로 19→14초까지 줄였지만, 남은 14초는 tracert 자체다
(`TRACE_MAX_HOPS` 12 × 3프로브 × `TRACE_PROBE_MS` 400ms).

`TRACE_PROBE_MS`를 400 → 200으로 줄이면 최악 7.2초가 된다. 국내·인근 홉은
50ms 안에 답하므로 대개 안전하지만, 먼 홉을 놓치면 하한이 실제보다 더 낮게
잡힌다. 아직 안 건드렸다.

`_trace_cache`는 메모리에만 있어서 도구를 재시작하면 같은 상대라도 다시
14초를 기다린다. 디스크에 남기면 없앨 수 있지만 **상대 IP를 파일로 저장하게
되므로 하지 않는다** (개인정보).

### 매칭 단계는 아직 못 봤다

이번 두 판 모두 이미 대전이 진행 중일 때 붙어서, 매칭 화면에서 잡담 IP가
걸러지는지는 확인하지 못했다. `MIN_RATE = 50`이 잡담(4~18pkt/s)을 막는다는
근거는 여전히 예전 로그뿐이다.

### 78pkt/s 건 — 이번엔 재현 안 됨

기동 스모크에서 `78pkt/s`(간격 161.9ms, ↑71↓7)가 `MIN_RATE`를 넘겨 상대로
뽑힌 적이 있다. 이번 두 판에서는 안 나타났다. 다시 나오면 `pick_opponent()`의
선정 조건에 `frame_paced`나 ↑↓ 대칭을 추가하는 걸 검토한다. 지금은 근거가
한 건뿐이라 손대지 않는다.

## 구조

`monitor.py` 한 파일. 세 개의 독립 루프로 돈다.

| 루프 | 주기 | 역할 |
|---|---|---|
| 캡처 (데몬 스레드) | 연속 | `AsyncSniffer`로 도착 시각 기록 |
| 핑 (데몬 스레드) | 1초 | EMA 누적, 메인을 막지 않음 |
| 표시 (메인) | 250ms | OSD 갱신. 콘솔 로그는 2초 |

측정은 빠르게, 화면은 천천히. 숫자가 초당 4번 넘게 바뀌면 사람이 못 읽는다.

캡처 범위는 SC6/steam.exe가 쥔 UDP 포트로 한정한다(`psutil.net_connections`).
이 목록은 스냅샷이라 요동치므로 `PortSet`이 세션 동안 합집합으로 누적한다 — 스니퍼를
다시 띄우는 순간의 패킷을 잃지 않기 위해서다. 한 번도 못 읽으면 차단 목록 방식
(`FALLBACK_BPF`)으로 폴백.

> 상대 IP는 개인정보다. 저장하거나 외부에 공유하지 말 것.
